# 0011. Elasticsearch и векторное хранилище необязательны

**Контекст.** ADR-0003 описывает поиск норм как гибрид Elasticsearch +
Milvus/Chroma, ADR-0009 включает оба сервиса в проверку готовности. На
площадках, где эти сервисы не заказаны, проверка документов не работала
совсем: задача падала на первом обращении к индексу.

**Решение.** Каждый сервис подключается независимо, признак — его адрес.
Пустой `ELASTICSEARCH_URL` — полнотекстовый поиск идёт в PostgreSQL
(`PgTextIndex`: колонка `npa_chunks.tsv`, GIN-индекс, словарь `russian`).
Пустой `VECTOR_STORE_URL` — векторного поиска нет, эмбеддинги не
запрашиваются. Слияние RRF работает с тем набором выдач, который есть.
Незаданный сервис не входит в проверку готовности. `PgTextIndex` лежит в
`gosdoc.docs_check.npa`, а не в `rag/`: ему нужна сессия БД, а `rag/search.py`
остаётся HTTP-клиентом без зависимости от схемы приложения.

Тексты норм в PostgreSQL — первичные данные, индексы — производные. Переход
между режимами: сменить адреса и выполнить `gosdoc reindex-npa --wait`
(порядок — в руководстве администратора, раздел 3.2); обратно — только
очистить адреса.

**Последствия.** Минимальная установка — PostgreSQL, Redis, RabbitMQ и
модель. Без векторного поиска хуже находятся нормы, близкие по смыслу, но
сформулированные другими словами; полный режим остаётся рекомендуемым.
Правило видимости актов организации записано дважды: в `rag/search.py` и в
SQL-запросе `PgTextIndex` — при изменении ADR-0006 править оба места.
Пересматривает ADR-0003 (состав поиска) и ADR-0009 (проверка готовности).
