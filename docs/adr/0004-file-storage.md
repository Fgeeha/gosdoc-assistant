# 0004. Хранилище файлов: FileStorage с тремя бэкендами

**Контекст.** MinIO на платформе больше не обновляется. Целевое хранилище —
SeaweedFS (S3 gateway); в будущем возможен переход на RustFS или другое
S3-совместимое хранилище. API и воркеры работают в разных подах, общего тома
нет.

**Решение.** Интерфейс `FileStorage` (`gosdoc.core.storage`): `put`, `get`,
`delete`, `list`, `presigned_url`. Бэкенд выбирается `STORAGE_BACKEND`:

| Бэкенд | Назначение | Детали |
|---|---|---|
| `s3` | прод (SeaweedFS) | boto3, path-style, endpoint/ключи/бакет/CA из конфигурации; только базовые операции — без versioning, object lock, событий бакетов и MinIO-специфичных API |
| `postgres` | запасной вариант без внешнего хранилища | таблица `file_blobs` (bytea), предел размера `STORAGE_MAX_FILE_MB` |
| `local` | отладка, PVC | каталог `STORAGE_LOCAL_PATH` |

Метаданные (владелец, организация, sha256, `expires_at`) всегда лежат в
таблице `files`, бэкенд хранит только байты по ключу `<organization_id>/<uuid>`.
Срок хранения (`FILE_RETENTION_DAYS`, 30 по умолчанию) реализован фоновой
задачей `cleanup_expired_files` по метаданным, а не lifecycle-правилами бакета.
Интеграционные тесты `s3` идут на SeaweedFS через testcontainers.

**Последствия.** Смена хранилища — это смена конфигурации. Файл целиком
помещается в память процесса, это допустимо при пределе в десятки мегабайт.
Если понадобятся большие файлы, нужен потоковый API (сейчас файл целиком читается в память, см. `api/files.py`).
