# Руководство администратора

Для администраторов системы, администраторов нормативной базы и
специалистов эксплуатации. Архитектура и принятые решения — в
[architecture.md](../architecture.md) и [adr](../adr).

## 1. Состав и зависимости

Приложение — три образа на Astra Linux (или РЕД ОС):

| Образ | Что делает |
|---|---|
| `gosdoc-api` | веб-API (FastAPI), миграции, служебные команды `gosdoc …` |
| `gosdoc-worker` | фоновые задачи: таблицы, PDF писем, проверка документов, индексация НПА, очистка; содержит LibreOffice и Tesseract (rus) |
| `gosdoc-frontend` | nginx: интерфейс и проксирование `/api/` |

Внешние сервисы заказываются на платформе ЦИТ и в чарт не входят:
PostgreSQL 14+, Redis, RabbitMQ, Elasticsearch 8 (с анализатором `russian`),
Milvus (REST API v2), S3-хранилище (SeaweedFS), Inference (OpenAI-совместимый
API: чат и `/v1/embeddings`), при необходимости — LDAP/AD, Airflow, MLFlow,
Evidently, Loki.

Без PostgreSQL и Redis приложение не работает (readiness отдаёт 503). Без
остальных сервисов работают вход и те модули, которым сервис не нужен;
состояние всех зависимостей видно в ответе `/health/ready`.

## 2. Установка

### 2.1 Образы

```bash
make images BASE_IMAGE=registry.astralinux.ru/astra/ubi18 \
  PIP_INDEX_URL=https://<зеркало PyPI>/simple NPM_REGISTRY=https://<зеркало npm>/ \
  IMAGE_PREFIX=<реестр>/gosdoc/gosdoc IMAGE_TAG=1.0.0
```

Для РЕД ОС — `BASE_IMAGE=registry.red-soft.ru/ubi8/ubi`. Если нужного пакета
нет в репозитории ОС, сборка останавливается с сообщением о пакете — базовый
образ не подменяется (ADR-0007). Python-зависимости ставятся из зеркала по
версиям и хешам `uv.lock`.

### 2.2 Секреты и CA

Secret (например `gosdoc-secret`) с ключами:

| Ключ | Значение |
|---|---|
| `DATABASE_URL` | `postgresql+psycopg://user:pass@pg.<домен>:5432/gosdoc?sslmode=verify-full&sslrootcert=/etc/gosdoc/ca/ca.pem` |
| `RABBITMQ_URL` | `amqps://user:pass@mq.<домен>:5671/` |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | ключи бакета |
| `LLM_API_KEY`, `EMBEDDINGS_API_KEY` | ключи Inference (если требуются) |
| `SERVICE_TOKEN` | случайная строка 32+ символов для DAG Airflow |
| `MLFLOW_TOKEN` | токен MLFlow (если требуется) |
| `GOSDOC_ADMIN_PASSWORD` | пароль первого администратора `admin` (20+ символов) |

Корневой CA — ConfigMap или Secret (ключ `ca.pem`), указывается в
`caBundle.configMapName` или `caBundle.secretName`. Путь передаётся
приложению в `CA_BUNDLE` и используется для TLS к S3, Inference,
Elasticsearch, Milvus, LDAP, MLFlow; к PostgreSQL — через `sslrootcert` в
`DATABASE_URL`.

### 2.3 Helm

```bash
helm upgrade --install gosdoc deploy/helm/gosdoc -n gosdoc -f values.yaml
```

Пример значений — `deploy/helm/gosdoc/values-example.yaml`. Порядок запуска:
Job миграций (ждёт PostgreSQL, создаёт бакет, применяет миграции, создаёт
`admin`, если его нет) → api и воркеры (initContainer ждёт зависимости и
актуальную схему БД) → frontend. При `ENVIRONMENT=prod` приложение не
стартует, если в настройках остались пароли dev-окружения или
`SESSION_COOKIE_SECURE=false`.

Очереди воркеров: `tables`, `letters`, `docs_check`, `npa`, `maintenance`.
По умолчанию все обрабатывает одна группа; тяжёлые (`docs_check`, `npa`)
можно вынести в отдельную группу `worker.groups` со своим числом реплик.

### 2.4 Airflow

Скопируйте `airflow/dags/*.py` в каталог DAG заказанного Airflow и задайте
Variables: `gosdoc_api_url` (адрес ingress), `gosdoc_service_token`
(= `SERVICE_TOKEN`), `gosdoc_ca_bundle` (путь к CA на воркерах Airflow);
для отчётов качества — `gosdoc_evidently_url`, `gosdoc_evidently_project`
и пакет `evidently` в окружении Airflow.

| DAG | Расписание | Что делает |
|---|---|---|
| `gosdoc_npa_update` | ежедневно 02:00 | доиндексация не проиндексированных редакций; по воскресеньям — вся база |
| `gosdoc_maintenance` | ежедневно 03:30 | удаление файлов с истёкшим сроком хранения |
| `gosdoc_quality` | ежедневно 05:00 | версии промптов → MLFlow, статистика замечаний → Evidently |

## 3. Настройки

Все параметры — переменные окружения (в чарте — `config` и Secret). Основные:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_BASE_URL`, `LLM_MODEL` | — | сервис Inference и модель |
| `LLM_MAX_CONTEXT` | 8192 | контекст модели в токенах; от него зависят размер фрагментов НПА и объём норм в запросе |
| `EMBEDDINGS_BASE_URL`, `EMBEDDINGS_MODEL` | как у LLM | модель эмбеддингов (может быть отдельным сервисом) |
| `VECTOR_STORE` | chroma | `milvus` в проде |
| `STORAGE_BACKEND` | s3 | `s3` / `postgres` / `local` |
| `FILE_RETENTION_DAYS` | 30 | срок хранения пользовательских файлов (ПДн) |
| `STORAGE_MAX_FILE_MB` | 50 | максимальный размер файла |
| `AUTH_PROVIDER` | local | `local` или `ldap` |
| `AUTH_MAX_FAILED_ATTEMPTS`, `AUTH_LOCKOUT_MINUTES` | 5, 15 | блокировка после неудачных входов |
| `AUTH_MIN_PASSWORD_LENGTH` | 12 | минимальная длина пароля |
| `SESSION_TTL_MINUTES` | 480 | сессия продлевается при каждом запросе |

После смены модели эмбеддингов запустите полную переиндексацию (DAG в
воскресенье или «переиндексировать» у каждого акта).

### 3.1 Вход через AD/LDAP

```
AUTH_PROVIDER=ldap
LDAP_URL=ldaps://dc.<домен>
LDAP_USER_DN_TEMPLATE={login}@<домен>
LDAP_SEARCH_BASE=DC=<домен>,DC=local
LDAP_GROUP_ROLES={"CN=GosDoc-Users,OU=Groups,DC=...": "user", "GosDoc-NPA": "npa_admin"}
```

Сертификат сервера каталога проверяется всегда. Роли назначаются по группам
при каждом входе; пользователь без разрешённой группы не входит. Пароли AD в
системе не хранятся и не меняются.

## 4. Работа администратора системы

### Пользователи и роли

Раздел «Пользователи». Новому пользователю задаётся временный пароль — при
первом входе система потребует его сменить. Изменение ролей, отключение и
сброс пароля завершают все сессии пользователя. После неудачных попыток
входа учётную запись можно разблокировать кнопкой «Разблокировать».

| Роль | Права |
|---|---|
| Пользователь | свои файлы, проверки, письма, таблицы; общие шаблоны маппинга |
| Руководитель | + работы сотрудников своего подразделения, утверждение писем |
| Администратор нормативной базы | загрузка и ведение ведомственных актов |
| Администратор системы | пользователи, бланки, настройки организации, календарь, журнал, общие акты |

Подразделение руководителя и сотрудников должно быть записано одинаково —
по нему определяется доступ руководителя.

### Организация, бланки, календарь

Раздел «Организация»:

- наименование и справочные данные для встроенного бланка, должность и
  расшифровка подписи по умолчанию;
- маска исходящего номера — регулярное выражение (например `\d{2}-\d{2}/\d+`);
  письмо с номером не по маске нельзя утвердить;
- бланки писем — DOCX-шаблоны docxtpl. Доступные переменные: `org_name`,
  `org_details` (список), `date`, `number`, `incoming_ref`, `addressee`,
  `title`, `greeting`, `paragraphs` (список), `closing`, `attachments`
  (список), `signer_position`, `signer_name`, `executor`, `executor_phone`.
  Бланк с неизвестными переменными не загрузится. Пример —
  `tests/fixtures/letters/blank.docx`;
- производственный календарь: суббота, воскресенье и праздники ст. 112 ТК РФ
  учитываются автоматически; переносы выходных и рабочие субботы вносятся
  каждый год по постановлению Правительства.

### Журнал действий

Раздел «Журнал действий»: вход и выход, неудачные попытки, загрузка и
скачивание файлов, создание и изменение писем, запуск проверок и переносов,
изменения пользователей, настроек и нормативной базы, запуски регламентных
задач. Записи нельзя изменить или удалить — это запрещено на уровне БД.
Рекомендуется дополнительно отозвать у роли приложения права на изменение
и очистку таблицы `audit_log`.

## 5. Нормативная база

Раздел «Нормативная база» (роль «Администратор нормативной базы»; общие для
всех организаций акты — «Администратор системы»).

- Загружайте официальные тексты в DOCX, HTML или PDF с текстовым слоем —
  по одному, пакетом или zip-архивом.
- Вид, номер и дата акта определяются по заголовку («Федеральный закон от
  27.07.2006 № 152-ФЗ»), дата редакции — по «в ред. от …». Если её в тексте
  нет, укажите «редакция действует с» перед загрузкой.
- Повторная загрузка того же акта — новая редакция; сроки действия
  редакций пересчитываются автоматически. Загрузка с той же датой редакции
  заменяет текст.
- Утративший силу акт отмечается вручную («статус»): дата и каким актом
  отменён — этот текст попадёт в замечание пользователю.
- Индексация идёт в фоне; ошибка индексации видна у редакции, её повторит
  ночной DAG или кнопка «переиндексировать».
- Все изменения — в «Журнале изменений».

Структура текста для разбивки на фрагменты: «Статья N. Название», части
«1. …», пункты «1) …». Документы без статей (постановления, приказы)
разбиваются по пунктам «1.».

## 6. Безопасность и 152-ФЗ

- Внешних обращений нет: модель, поиск и хранилище — в контуре. Сетевой
  доступ подов наружу ограничивается политиками кластера.
- В модель не передаются данные строк таблиц — только названия колонок и
  «форма» значений (например `Аааааа А.А.`). При проверке документа
  передаются отдельные абзацы и тексты норм, при подготовке письма —
  описание задачи и текст входящего.
- В логах ПДн (СНИЛС, ИНН, паспорт, телефон, e-mail, номер карты)
  маскируются; тексты документов и запросов к модели в логи не пишутся.
- Пользовательские загрузки и результаты хранятся `FILE_RETENTION_DAYS`
  дней и удаляются автоматически вместе с содержимым. Бланки, шаблоны
  маппинга (только заголовки) и тексты НПА хранятся бессрочно.
- Всё, что подготовлено моделью, помечено как черновик.

## 7. Эксплуатация

| Задача | Как |
|---|---|
| Состояние | `GET /health/ready` — список зависимостей и их статус |
| Логи | JSON в stdout, Loki — `deploy/monitoring/README.md` |
| Обновление | `helm upgrade` с новым `image.tag`; миграции применяет Job автоматически |
| Резервное копирование | PostgreSQL (все данные, кроме содержимого файлов) и бакет S3 — средствами платформы; индексы Elasticsearch и Milvus восстанавливаются полной переиндексацией |
| Сбой задачи | задачи не повторяются автоматически: пользователь запускает заново, НПА — ночной DAG или «переиндексировать» |
| Пароль admin утерян | сброс другим администратором в «Пользователях» или новый администратор командой `gosdoc create-user` |

Служебные команды (в контейнере api): `gosdoc wait-deps`,
`gosdoc wait-migrations`, `gosdoc init-storage`,
`gosdoc cleanup-files [--every N]`,
`gosdoc create-user --login … --roles … --password-env VAR`.
