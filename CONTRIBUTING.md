# Правила участия в разработке

## Ветки

| Ветка | Назначение |
|---|---|
| `Master` | выпущенные версии; каждый коммит — релиз с тегом `vX.Y.Z` |
| `develop` | интеграционная ветка; всегда проходит `make check` |
| `feature/<кратко>` | новая функциональность, от `develop` |
| `bugfix/<кратко>` | исправление, от `develop` |
| `release/<X.Y.Z>` | подготовка релиза, от `develop` |
| `hotfix/<кратко>` | срочное исправление выпущенной версии, от `Master` |

Напрямую в `Master` и `develop` не коммитим — только слиянием рабочих веток.

## Как вести рабочую ветку

1. Создать ветку от свежего `develop`:
   `git switch develop && git pull && git switch -c feature/<кратко>`.
2. Синхронизироваться с `develop` через rebase, а не merge:
   `git fetch && git rebase origin/develop`. Rebase допустим, пока ветку
   никто, кроме автора, не взял в работу; после этого — только
   `git push --force-with-lease`.
3. Перед слиянием — `make check` (ruff, mypy, tsc, все тесты). Если менялся
   Helm-чарт — ещё `make helm-lint`; новые миграции — `make migrate` на чистой
   базе.

## Слияние в develop

- Только `git merge --no-ff`: в истории `develop` каждая рабочая ветка видна
  отдельным коммитом слияния. Squash и fast-forward не используем.
- Сообщение коммита слияния:
  `chore: слияние feature/<кратко> в develop (<что сделано>)`.
- Ветки, построенные цепочкой одна на другой, сливаются по порядку, начиная
  с ближайшей к `develop`; каждая — отдельным `--no-ff`.
- После слияния `develop` снова должен проходить `make check`.
- Слитую ветку удаляем локально и в репозитории.

## Релиз

1. `release/<X.Y.Z>` от `develop`: в ней только версия, документация и
   исправления найденного при проверке.
2. `git merge --no-ff` в `Master`, тег `vX.Y.Z`, затем `git merge --no-ff`
   обратно в `develop`.
3. `hotfix/*` сливается так же — в `Master` с новым тегом и в `develop`.

## Коммиты

- [Conventional Commits](https://www.conventionalcommits.org/ru/):
  `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `build:`, `ci:`, `chore:`.
- Сообщение на русском, кратко и по существу, без эмодзи.
- Один коммит — одно логическое изменение; код, тесты и документация к нему
  идут вместе.
- В репозиторий не попадают `.env`, ключи, сертификаты, пароли, внутренние
  адреса и персональные данные (в том числе в тестовых фикстурах) — только
  `.env.example` и вымышленные данные.
- `git user.name` и `git user.email` — свои настоящие; трейлеры
  `Co-Authored-By` добавляются только для реальных соавторов-людей.
